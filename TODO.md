# TODO по ТЗ LinQ: frontend / backend / DevOps

Область работ намеренно ограничена приложением и эксплуатацией. В этот список не
входят обучение, дообучение, разметка, новые детекторы, новые классы моделей,
квантование, компиляция LinQ и оценка качества моделей. Worker должен использовать
существующие типы событий и результаты инференса через текущий контракт.

- [ ] **Состояние связи и потерянные live-события.** При разрыве WebSocket показать

  восстановления догружать события с сервера, а не только обновлять текущий экран.

## Backend

### P0

- [ ] **Идемпотентность событий после рестарта.** Перенести ключ активного
  нарушения и cooldown из памяти `RuleEngine` в backend/БД или добавить протокол
  восстановления состояния. После перезапуска worker продолжающееся нарушение не
  должно создавать второе событие/уведомление. Добавить e2e-тест с рестартом worker.

- [ ] **Per-camera configuration API.** Расширить модели и `/internal/config` для
  overrides правил на камеру, включения/выключения типов событий и версии
  конфигурации. Сохранение должно быть атомарным, валидироваться Pydantic и
  применяться worker без ручного рестарта.

- [ ] **Стабильный контракт событий.** Вынести описание типов событий, severity,
  доступных параметров и области применения в единый backend-реестр. API журнала,
  WebSocket, webhook и analytics должны использовать один источник метаданных;
  неизвестный тип должен корректно отображаться как `unknown`, а не ломать выдачу.

- [ ] **Сквозная идемпотентность доставки.** Для webhook и Telegram сохранять
  event/action/idempotency key, чтобы retry, reconnect и повторная доставка очереди
  не отправляли дубль. Оставить текущие retry/backoff, добавив уникальное
  ограничение и тесты на повторный запрос.

### P1

- [ ] **Экспорт размеченных событий без работы с моделями.** Добавить endpoint и
  фоновую задачу, которая по фильтрам выгружает метаданные события, review,
  snapshot/clip-ссылки и latency в ZIP/JSONL. Это только операционный экспорт для
  аналитики и аудита; обучение и изменение моделей в scope не входят.

- [ ] **Операционный мониторинг.** Добавить Prometheus-compatible метрики или
  эквивалентный `/metrics`: ingest FPS, обработанные/пропущенные кадры,
  capture→event latency p50/p95, open events, webhook/Telegram success/error,
  размер очередей и возраст самой старой задачи.

- [ ] **Readiness/liveness и деградация.** Разделить health checks backend/worker,
  возвращать причину offline камеры и состояние конфигурации; при недоступности
  worker backend должен продолжать принимать UI-запросы и явно показывать stale
  status.

- [ ] **Консистентность конфигурации.** Добавить optimistic locking/version check
  при изменении камер, зон и правил, журнал изменений (кто/когда/что изменил) и
  защиту от применения устаревшего конфига worker.

### P2

- [ ] Добавить endpoint агрегированного отчёта за период с timezone, сравнением с
  предыдущим периодом и готовыми данными для frontend-графиков.
- [ ] Добавить backup/restore SQLite или перейти на production DB с миграциями,
  отдельным хранилищем media и проверкой восстановления.
- [ ] Расширить backend/e2e-тесты: рестарт и dedup, stale config, idempotent retry,
  export, metrics, права на media и пагинация больших журналов.
