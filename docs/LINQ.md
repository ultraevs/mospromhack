# Инференс на LinQ TPU

Как модели сервиса попадают на ускоритель LinQ, какая у них точность после квантования и сколько камер тянет TPU. SDK — `tpu_framework 2026.9.45` (компиляция). Инференс — облачная очередь TPU на стенде организаторов (RabbitMQ + `tpu_pycloud_format`), локальный `pytpu` тоже поддержан.

## 1. Маршрут модели

```
models/<m>/best.onnx (YOLOv8s, [1,3,640,640])
  -> срез головы: на TPU всё до декодированных xy, wh и Sigmoid классов      scripts/linq_compile.py
  -> preliminary_model_conditioning -> calibrate_torch на реальных кадрах -> quantize (int8)
  -> compile_ (TPU_H1M, пресет O1) -> models/<m>/linq/<m>_b1_o1_h1m.tpu + meta.yaml

кадр -> letterbox/preprocess (как для onnx) -> TPU (облако или pytpu) -> хвост в numpy -> decode + NMS -> трекинг, правила
                                                 worker/app/detector/linq.py
```

Сервис вокруг детектора не меняется: `LinqDetector` возвращает тот же `[N, 4+nc, 8400]` float32, что и `OnnxDetector`. Включается `worker.detector: linq` в `config.yaml`.

### Срез головы

В документации SDK модели YOLO с detect-головой (`yolo12m`) обрезаны по `/model.21/Div_1`, `/model.21/Sub_1` и `/model.21/Sigmoid`. Остаток уходит в постобработку. У YOLOv8s голова того же вида, `linq_compile.py --cut auto` находит её сам:

```
output0 = Concat( Mul( Concat(/model.22/Div_1 (xy), /model.22/Sub_1 (wh)), strides ), /model.22/Sigmoid (классы) )
```

DFL, softmax и декод рамок считаются на TPU. На процессоре остаются два `Concat` и умножение на страйды 8/16/32 (`yolo_tail` в `worker/app/detector/linq.py`). Страйды берутся из модели в `strides.npy`, onnxruntime на стенде не нужен. Расхождение numpy-хвоста с отрезанным `tail.onnx` — 0.

Тензоры программы (вывод `linq_compile.py`):

| тензор | форма | внутри TPU |
|---|---|---|
| `images` (вход) | (1, 3, 640, 640) float32 | дополняется до 4 каналов |
| `/model.22/Div_1_output_0` | (1, 2, 8400) | 8448 |
| `/model.22/Sub_1_output_0` | (1, 2, 8400) | 8448 |
| `/model.22/Sigmoid_output_0` | (1, nc, 8400) | 8448, масштаб на каждый якорь |

Упаковка и распаковка (масштаб, int8, паддинг) делаются рантаймом по метаданным программы. Вход и выход — float32. Свой raw-путь — в разделе 5.

### Модель people

COCO yolov8s для людей и техники. `scripts/make_people_model.py` урезает голову до 5 классов (person, car, motorcycle, bus, truck): в последних conv `cv3` оставлены только эти выходные каналы. На float рамки и скоры совпадают с полной моделью с точностью 0.0. Выход классов на TPU 5×8448 вместо 80×8448.

## 2. Окружение SDK и шаги

SDK есть только под Linux x86_64 и Python 3.12.11 (tensorflow 2.20, torch 2.9.1, numpy 1.26.4), поэтому он собран в Docker. Колёса SDK в репозиторий не входят: их выдают организаторы.

```powershell
powershell -ExecutionPolicy Bypass -File scripts\linq_sdk.ps1 -Build          # образ linq-sdk, ~2 ГБ, torch без CUDA
powershell -ExecutionPolicy Bypass -File scripts\linq_sdk.ps1                 # bash в контейнере: /repo — репозиторий, /merged — MERGED_DIR из .env
```

Проверка SDK: эталонный `compile.py` из поставки собирает `torch_resnet50_b1_o1_h1m.tpu` за 57 с. В версии 2026.9.45 пресет `O5_FGS` из документации не экспортируется, доступны `O1`, `O3`, `O5`.

Шаги внутри контейнера:

```bash
# 1. калибровочный набор: 128 картинок обучающей выборки поровну по источникам + 64 кадра из роликов
python scripts/linq_calib.py --model ppe --images /merged/ppe/images/train --videos data/videos
# 2. срез, квантование, компиляция (около 1,5 минуты на модель)
python scripts/linq_compile.py --model ppe --preset o1 --calib data/linq/calib_ppe.npy --n-calib 64
# 3. точность int8 без TPU: квантованная голова через as_torch_graph + хвост, против float best.onnx на val
python scripts/linq_eval.py --model ppe --merged /merged --limit 300
# 4. эталон для сверки на стенде и архив для загрузки в Jupyter
python scripts/linq_eval.py --model ppe --merged /merged --ref 16
python scripts/linq_pack.py --models ppe hazard     # -> data/linq/linq_stand.zip
```

`linq_compile.py` дополнительно принимает `--samplewise 99.9` и `--act-percentile` (перцентили калибровки), `--finetune N` (дообучение порогов `fine_tune_torch`), `--cut none|auto|имена`, `--preset o1|o3|o5`.

people (~3.5 мин: квантование 96 с, компиляция 102 с):

```bash
python scripts/linq_calib.py --model people --images /merged/ppe/images/train --videos data/videos
python scripts/linq_compile.py --model people --preset o1 --calib data/linq/calib_people.npy --n-calib 64
python scripts/linq_eval.py --model people --merged /m --ref 48    # /m/people смонтирован на merged/ppe
```

heads v2: `linq_calib.py --images merged/heads2/images/train`, `linq_compile.py --model heads --preset o1`, компиляция 72 с. Калибровка heads — 64 картинки датасета и 115 плиток роликов (`linq_calib.py --tiles`, `--n-calib 0`). `--n-calib 64` берёт каждый N-й кадр и на небольшом наборе не доходит до кадров роликов, поэтому плитки задаются явно.

Артефакты лежат в `models/<m>/linq/` и в git не попадают, кроме `meta.yaml`. `meta.yaml` описывает программу: вход, выходы TPU, хвост, параметры калибровки, int8-пороги, время этапов.

Облако держит программу в памяти TPU по пути и новый файл по старому пути не перечитывает. После перекомпиляции программа кладётся под новым именем (например, `heads2c_b1_o1_h1m.tpu`).

## 4. Пороги под int8

Квантование int8 сжимает оценки классов: у heads в 4–8 раз, у ppe примерно в 1.6 раза. Ранжирование сохраняется, поэтому mAP почти не падает, но пороги float на TPU режут почти все детекции. С порогами float на стенде правило «без каски» срабатывало 0 из 9 раз.

Оценки «без каски» на одних и тех же плитках (`scripts/linq_heads_check.py`):

| | onnx float32 | симуляция int8 (SDK) | TPU стенда |
|---|---|---|---|
| heads, «без каски», solo-worker 8 с | 0.76 | 0.099 | 0.099 |
| heads, то же, 25 с | 0.76 | 0.205 | 0.205 |
| ppe, «без каски», 8 с | 0.77 | 0.483 | 0.48 |

TPU совпадает с симуляцией до третьего знака, с `raw=True` и `raw=False`. Упаковка, облако и хвост на оценки не влияют.

`scripts/linq_thresholds.py` подбирает пороги по максимуму F1 на симуляции int8 и пишет их в `models/<m>/linq/meta.yaml`. `LinqDetector` берёт их оттуда, `Worker` подменяет пороги спеков только для linq, onnx не трогается.

| heads, 150 картинок val | порог float → int8 | P / R при int8 | P / R float при своём пороге |
|---|---|---|---|
| helmet | 0.334 → 0.087 | 0.81 / 0.88 | 0.91 / 0.91 |
| no_helmet | 0.444 → 0.058 | 0.91 / 0.89 | 0.92 / 0.84 |

ppe и hazard (150 картинок val):
- ppe: person 0.515 → 0.159, no_helmet 0.48 → 0.154, no_mask 0.429 → 0.076;
- hazard: fire 0.338 → 0.059, cigarette 0.362 → 0.053;
- редкие классы (меньше 40 рамок в выборке: helmet, vest, mask, vehicle) берут порог float × медианное сжатие крупных классов (у ppe ×0.26);
- если порог float поднят руками над max F1, переносится тот же сдвиг: no_helmet ×1.24, smoke ×2.4;
- дым поставлен руками на 0.3: на solo-worker пыльная стена давала ложный дым с уверенностью 0.16–0.21. Роликов с настоящим дымом нет, полнота по дыму не проверена.

С int8-порогами у ppe и hazard огонь на fire-explosion ловится через 0.9 с после появления пламени, уверенность 0.26–0.30.

## 5. Работа со стендом

TPU стоит у организаторов, доступ через VPN и JupyterHub. `pytpu` и `/dev/tpu` в Jupyter нет: ускоритель отдаётся облачной очередью.

- **Брокер.** RabbitMQ на `10.0.114.30:5672`, exchange `tpu.direct`, ключ `input`.
- **Запрос.** Тело — `PyTask` из `tpu_pycloud_format`. В заголовке `uri` — путь к программе: `file:///auto/cache/<login>/<prog>.tpu?raw=False`. Ответ приходит в очередь из `response_routing_keys` и содержит `inference_time`.
- **Детектор.** `LinqDetector(transport="cloud")`. Каждый поток держит своё соединение и exclusive-очередь, пачка кадров публикуется целиком и собирается по message id. Настройки — `worker.linq` в `config.yaml`, логин — `LINQ_LOGIN`.
- **Доступ.** `scripts/linq_stand.py` работает с Jupyter: cookie-сессия хаба, загрузка и скачивание файлов, выполнение кода в ядре. VPN поднимается в отдельном контейнере (`docker/linq-vpn.Dockerfile`, `scripts/linq_stand.ps1`), сеть хоста не трогается.

Сверка TPU с квантованной симуляцией (`linq_bench.py`, эталон `ref_<m>.npz` от `linq_eval.py --ref`):

| ppe | значение |
|---|---|
| совпадение детекций TPU и симуляции | 1.0 |
| макс. разница скоров | 0.0 |
| совпадение детекций TPU и float32 | 0.696 (флипы около порогов) |

people на стенде (raw): совпадение с симуляцией 1.0, разница скоров 0.0.

### Raw int8-упаковка

С `raw=False` облако получает float32 и пакует его на своей стороне: на кадр 4.9 МБ туда и ~370 КБ обратно, вызов ~1 с при 40 мс на TPU. С `raw=True` облако берёт готовые uint8-блоки, упаковку и распаковку делает `worker/app/detector/linq_raw.py` (numpy, без SDK).

- **Раскладка** берётся из `metadata.json` внутри `.tpu`: `user_shape/order`, `tpu_shape/order`, `scales`, `padding`, `ddr_word_len`.
  - Вход `images`: NCHW float → int8 `rint(x·127)`, каналы добиты до 4, лежит как HWC4. Итого (51200, 32) uint8, 1.6 МБ.
  - Выходы: (C/128, W, 1, 128) int8 или fp16, хвост 48 якорей обрезается, `·scale`. Итого 135 КБ.
- **Кадр сразу в int8.** `ImagePacker` превращает BGR uint8 после letterbox в raw одним `cv2.LUT` по RGBA (таблица на 256 значений, 4-й канал нулевой), без float-тензора. 3.4 мс против 54 мс у пути «float-препроцесс + pack». Воркер в raw зовёт `detector.prepare()` вместо `preprocess()` (`_infer_packed` в `worker/app/main.py`).
- **Сверка.** Эталон снят SDK-шным `tpu_io.pack/unpack` на программе ppe, совпадение бит в бит (`worker/tests/test_linq_raw.py`). На стенде: совпадение детекций с симуляцией 1.0, разница скоров 0.0.
- **Включение.** `worker.linq.raw: true` в `config.yaml` (по умолчанию) или `--raw` у `linq_bench.py`. Программа `.tpu` должна лежать локально в `models/<m>/linq/` рядом с `meta.yaml` и совпадать с той, что в `/auto/cache/<login>/` (сверять `md5sum`).

Разбивка вызова по этапам, ppe, на кадр, CPU контейнера свободен:

| режим | prepare | облако | TPU (`inference_time`) | итого | кадров/с |
|---|---|---|---|---|---|
| raw=False, пачка 1 | — | 157 мс | 50 мс | 158 мс | 6.3 |
| raw=True, пачка 1 | 6.7 мс | 72 мс | 35 мс | 80 мс | 12.5 |
| raw=False, пачка 4 | — | 68 мс | 38 мс | 69 мс | 14.5 |
| raw=True, пачка 4 | 5.2 мс | 27 мс | 41 мс | 34 мс | 29 |
| raw=False, пачка 8 | — | 54 мс | 42 мс | 56 мс | 17.9 |

Пачка обрабатывается облаком параллельно, поэтому «облако на кадр» меньше `inference_time` одного кадра. Raw быстрее в 2 раза на любой пачке. people: пачка 1 — 70 мс/кадр, пачка 8 — 26 мс/кадр (38 кадров/с), как у ppe.

### Ресурсы контейнера Jupyter

Контейнеру выдано 1.5 ядра (`cpu.max 150000 100000`) и 4 ГБ памяти, хотя `nproc` показывает 64. Ядра ноутбуков, мост, воркер и фоновые процессы делят эти 1.5 ядра.

- Перед замерами смотреть `ps aux --sort=-%cpu` и `/sys/fs/cgroup/cpu.stat` (`nr_throttled`). Фоновый `linq_eval.py` занимает до 141% и замедляет всё остальное (таблица выше).
- Не строить float-тензоры на весь кадр: `np.rint` по кадру при троттлинге — 220 мс.

### Весь воркер на стенде

`scripts/linq_pipeline.py` запускает настоящий `Worker` на стенде без backend: клиент и отправка рамок заменены заглушками, которые считают события и задержку. Путь: зацикленный ролик → ffmpeg → ppe + people + hazard на TPU (raw) → проход по головам и сигаретам → трекер и правила → события.

```bash
python scripts/linq_remote.py sync
python scripts/linq_remote.py sh "python scripts/linq_pipeline.py --cams 1 2 4 --seconds 60 --tag stand"
python scripts/linq_remote.py sh "python scripts/linq_pipeline.py --cams 2 4 6 --videos factory_floor_sub.mp4 warehouse_sub.mp4 --tag stand_sub"
```

На стенде ffmpeg 4.4 без `-readrate_initial_burst`, поэтому ролики крутятся через `-re -stream_loop`. Отчёт — `data/linq/pipeline_<tag>.json`. Задержка события — от захвата кадра до `post_event`, включая ожидание правил (окно 4 с не входит: считается от кадра, на котором сработало правило).

|---|---|---|---|---|---|---|
| float32 (облако пакует) | 1 / 2 / 4 | 4.2 / 2.5 / 1.6 | 4.2 / 4.9 / 6.4 | 0.53 / 0.70 / 1.00 | — | 661 / 861 / — мс |
| raw | 1 / 2 / 4 | 5.6 / 4.9 / 2.5 | 5.6 / 9.7 / 10.1 | 0.48 / 1.02 / 1.23 | 0.14 / 0.49 / 0.66 | 236 / 343 / 646 мс |
| raw + people параллельно + кэш упаковки | 2 / 4 / 6 | 5.4 / 2.6 / 0.9 | 10.8 / 10.5 / 5.2 | 0.94 / 1.28 / 1.44 | 0.40 / 0.72 / 0.98 | 259 / 686 / — мс |

| 1 | 4 / 6 | 4.4 / 2.2 | 17.4 / 12.9 | 541 / 782 мс |
| 2 | 4 / 6 | 4.5 / 2.4 | 18.0 / 14.2 | 809 / 1102 мс |

Вызов облака удлиняется пропорционально числу кадров в полёте: предел — пропускная способность общего облачного TPU для логина, а не воркер.

### Посредник relay

Чтобы обрабатывать на TPU живую камеру, подключённую к ноутбуку: сырые int8-тензоры (~1.2 МБ на кадр) по VPN не проходят. Воркер на ноутбуке шлёт JPEG в свою очередь на брокере стенда, `scripts/linq_relay.py serve` на стенде (в одной сети с облаком TPU) гонит кадр через `LinqDetector` (raw, int8-пороги из `models/<m>/linq/meta.yaml`) и возвращает рамки JSON. Плитки голов, второй проход по головам, склейка people/heads и правила остаются в воркере: `RelayDetector` (`worker/app/detector/relay.py`) подменяет только `prepare/infer`. Если посредник не ответил за `RELAY_TIMEOUT_S` (5 с) или брокер недоступен — пустые детекции и ошибка в логе раз в 10 с, воркер продолжает работу.

```bash
# 1. код на стенд
MSYS_NO_PATHCONV=1 docker exec -w /repo linq-vpn python scripts/linq_remote.py --models=ppe sync
# 2. посредник на стенде, 4 обработчика, prefetch=1
MSYS_NO_PATHCONV=1 docker exec -w /repo linq-vpn python scripts/linq_remote.py sh \
  "nohup python scripts/linq_relay.py serve --workers 4 > /auto/cache/\$LINQ_LOGIN/relay.log 2>&1 &"
# 3. воркер: worker.detector: relay в config.yaml или DETECTOR=relay в окружении процесса.
#    нужна сеть до брокера (VPN), логин — LINQ_LOGIN из .env или файл логинов как у linq_stand.py
# остановить (ядер на стенде 1.5):
MSYS_NO_PATHCONV=1 docker exec -w /repo linq-vpn python scripts/linq_remote.py sh "pkill -f '[l]inq_relay.py serve'"
```

`scripts/linq_relay.py bench` внутри linq-vpn (путь по VPN), factory_floor 1280 px, кадр как у воркера: ppe + people + heads по двум плиткам параллельно (hazard раз в секунду, не входит), 20 с на точку:

| JPEG q | параллельных камер | к/с всего | к/с на камеру | задержка кадра p50 / p95 | трафик на кадр туда / назад |
|---|---|---|---|---|---|
| 85 | 1 | 0.87–0.98 | 0.87–0.98 | 968–1075 / 1267–1541 мс | 335 / 0.5 КБ |
| 85 | 2 | 1.58 | 0.79 | 1121–1183 / 2097–2144 мс | 335 / 0.5 КБ |
| 85 | 4 | 2.75 | 0.69 | 1343 / 2347 мс | 335 / 0.4 КБ |
| 70 | 1 | 1.01 | 1.01 | 941 / 1129 мс | 233 / 0.4 КБ |
| 70 | 2 | 1.72 | 0.86 | 1056 / 2065 мс | 233 / 0.4 КБ |

- Стенд на запрос (декод JPEG + TPU + decode): ppe ~230 мс, people ~210–235, heads (2 плитки) ~135–155. С 1 до 4 параллельных почти не растёт, суммарные к/с растут почти линейно (0.87 → 1.58 → 2.75).
- Предел — VPN: запрос ppe 830–850 мс туда-обратно при 230 мс на стенде. Трафик на кадр — 4 JPEG 640×640 (ppe, people, 2 плитки heads), на камеру ~0.3 МБ/с против ~5 МБ/с у сырых тензоров.
- `RELAY_JPEG_QUALITY=70` срезает трафик на 30% и даёт +10% к/с; влияние на точность не измерено, по умолчанию 85.
- Возможное улучшение: слать один JPEG кадра, а плитки и входы ppe/people нарезать на стенде — трафик ~1/4.

### Воркер на стенде, веб локально

VPN тянет около 0.6 МБ/с. Кадр 640×640 float32 — 4.9 МБ, около 9.5 с на кадр. Поэтому воркер работает на стенде, а backend, MediaMTX и UI — локально.

- **Мост** `scripts/linq_bridge.py`. На стенде (`stand`) он изображает бэк на `127.0.0.1:8000`: HTTP и WebSocket воркера уходят в очереди `<prefix>.req` и `<prefix>.ws` того же брокера. Локально (`local`) мост забирает их и отдаёт настоящему бэку, `X-Internal-Token` подставляется только локально. Через мост идут рамки и события — килобайты.
- **Видео.** Ролики лежат на обеих сторонах, воспроизведение синхронизировано по часам (`shared/sync.py`). Локальный мост переписывает `rtsp_url` файловых камер на `syncfile://<имя>`, воркер читает файл с того же смещения `(now - SYNC_EPOCH_S) % duration`, с которого его публикует backend. Кадр в UI совпадает с кадром, на котором считались рамки.
- **HLS.** Для просмотра через прокси без WebRTC — `VIDEO_MODE=hls`, поток ограничивается `STREAM_WIDTH` и `STREAM_MAXRATE`.

## 6. Производительность и ёмкость

### Скорость одиночных запросов

ppe, 640×640, запуск из Jupyter стенда:

| что | время |
|---|---|
| TPU, `inference_time` из ответа | ~6.8 мс/кадр, под общей нагрузкой 40–46 мс |
| запрос в облако целиком | 120–285 мс |
| 4 запроса в полёте | 15–15.8 кадра/с |

Несколько камер (`scripts/linq_cams.py`), каждая 6 кадров/с в своём потоке со своей очередью:

| камер | p50 | p95 | всего кадров/с | ошибок |
|---|---|---|---|---|
| 1 | 122 мс | 134 мс | 6 | 0 |
| 2 | 161 мс | 186 мс | 12 | 0 |
| 4 | 179 мс | 200 мс | 22.2 | 0 |

ppe и people одновременно, без декодирования, пачка 8: 54–60 к/с на две модели при `inference_time` ~37 мс на кадр (примерно 2 кадра параллельно).

### Сколько камер тянет один TPU

Конвейер как в `config.yaml`: ppe, people, hazard и heads v2 по двум плиткам кадра (`worker.tiles`). Цель — 6 кадров/с на камеру.

Цена камеры — ~25 инференсов TPU в секунду: ppe 6, people 6, heads 12 (две плитки), hazard 1. Без плиток 19.

Стенд общий для всех команд, `inference_time` в разное время суток — от 2 до 60 мс (3 мс — минимум, измеренный нами на пустом стенде).

| загрузка облака | `inference_time` | инференсов/с на чип | камер с плитками | без плиток |
|---|---|---|---|---|
| свободный чип | 2–3 мс | 330–500 | **13–20** | 17–26 |
| умеренная | ~37 мс | ~60 | 2 | 3 |
| пиковая | до 60 мс | ~30 | 1 | 1–2 |

- Строка «свободный чип» — расчёт по времени инференса, прогоном камер не проверена. Параллельная обработка пачки даст больше камер, накладные расходы облака — меньше.
- Две нижние строки подтверждены прогоном всего воркера (`linq_pipeline.py`, ролики 1280×720, inflight 1, пиковая нагрузка облака):

| камер | с плитками: к/с на камеру | всего | CPU, ядер | задержка события p50 | без плиток: к/с на камеру | всего | CPU, ядер |
|---|---|---|---|---|---|---|---|
| 1 | 5.2 | 5.2 | 0.73 | 231 мс | 6.0 | 6.0 | 0.57 |
| 2 | 4.6 | 9.1 | 1.12 | 567 мс | 5.1 | 10.2 | 1.03 |
| 4 | 1.9 | 7.5 | 1.32 | — | 2.2 | 8.9 | 1.29 |

- Предел — облачный TPU: вызов ppe растёт с числом камер почти линейно (117 → 245 → 521 мс), CPU не упирается.
- Плитки стоят 10–15% кадров; упаковка двух плиток — до 0.27 ядра.

Ёмкость по ресурсам при умеренной нагрузке облака (`inference_time` ~37 мс):

| ресурс | что меряли | сколько | камер по 6 к/с |
|---|---|---|---|
| облачный TPU для логина | ppe + people одновременно, пачка 8 | ~60 инференсов/с | ~4–5 (на камеру ~13 инференсов/с: ppe 6 + people 6 + hazard 1) |
| CPU контейнера 1.5 ядра | `linq_pipeline`, субпотоки, 4 камеры: 17.4 к/с при 0.96 ядра | ~0.055 ядра на кадр/с | ~4–5 при полной загрузке |
| весь воркер на стенде | субпотоки, inflight 2 | 18 к/с на 4 камерах | 3 камеры на полных 6 к/с |

Итог: один свободный чип LinQ — 13–20 камер в реальном времени со всеми моделями (расчёт); на общем облаке стенда — 1–2 камеры (замер). 4 к/с вместо 6 дают ещё ×1.5 камер. CPU контейнера стенда (1.5 ядра) тянет 4–5 камер, поэтому 13–20 относится к чипу рядом с полноценным процессором. На свободном TPU узким местом становится CPU (декодирование, правила).

## 8. Что учесть при внедрении

- **Батч.** Программы скомпилированы с batch 1. В облачном режиме `batch_limit` равен `worker.linq.batch`: столько кадров публикуется сразу, TPU обрабатывает их параллельно. С `pytpu` — по одному кадру.
- **Пороги.** Пороги float из `model.yaml` на int8 не переносятся (раздел 4). После каждой перекомпиляции — `linq_thresholds.py` и новое имя `.tpu`.
- **Вырезки.** Сигарета ищется моделью `hazard` на вырезках людей. Если TPU медленнее видеокарты, первым делом уменьшить `crop_pass.cigarette.max_per_tick`.
- **Процессор.** На onnxruntime узкое место — однопоточный главный цикл воркера (декодирование, предобработка, правила), а не инференс. С TPU это сохраняется. Сервер с нормальным CPU рядом с TPU, камеры отдают субпоток 6–10 к/с.
- **Сеть.** Кадры не возить по медленному каналу: воркер ставится рядом с TPU, наружу уходят рамки и события.
