# Контроль безопасности по видео

Сервис смотрит в камеры цеха и находит нарушения техники безопасности: человек без каски, жилета или маски, вход в запретную зону, курение, огонь и дым, бег, опасное сближение с техникой, падение, человек лежит неподвижно. На каждое нарушение приходит одно событие с кадром и клипом. Его разбирают в журнале, оно уходит в Telegram и во внешние системы.

Нейросети работают на российском ускорителе LinQ TPU (int8) или локально на видеокарте через ONNX Runtime. Логика одна, меняется только бэкенд инференса.

Хакатон «Открой#Моспром», кейс LinQ, 23–25 октября 2026.

## Результаты

Подробно, с методикой и сырыми данными: [docs/METRICS.md](docs/METRICS.md).

- **0 ложных тревог** на 23 размеченных нарушениях с наших роликов и на 145 с чужого видео, на котором ничего не настраивали.
- **16–18 из 23 нарушений** ловит настоящий сервис на TPU стенда, «без каски» — 9 из 9. Событие приходит в среднем через 2 с после начала нарушения.
- **int8 почти не теряет точность:** mAP50 отличается от float32 на −0.04…+0.005.
- **Модели на полной валидации, mAP50 [95% ДИ]:** каска по головам 0.913 [0.905–0.923], СИЗ 0.810 [0.771–0.848], огонь/дым/сигарета 0.722 [0.701–0.745].
- **Мелкие головы.** На обзорной камере голова занимает 6–10 px. Отдельная модель голов и разрезка кадра на две плитки подняли «без каски» на событиях с 4 из 9 до 7–9 из 9.
- **Ёмкость.** Камера при 6 к/с стоит около 25 инференсов TPU в секунду: на свободном чипе это 13–20 камер (расчёт по замеру 3 мс на инференс).

## Как устроено

```
камеры RTSP, видеофайлы, наборы картинок ─→ MediaMTX ─→ браузер (WebRTC)
                                             │
 worker   кадр 6 раз в секунду → модели ppe, people, heads, hazard (ONNX или LinQ TPU)
          → трекинг людей → правила с подтверждением во времени → событие, кадр, клип
                                             │
 backend  FastAPI + SQLite: камеры, зоны, правила, журнал, пользователи
          → интерфейс (React)   → Telegram   → вебхуки с подписью HMAC
```

Нарушение — это не один кадр, а признак, который держится во времени: например, 60% кадров за 4 с. Пока нарушение длится, повторов нет. Пороги правил редактируются в интерфейсе, обязательные СИЗ задаются на камеру и на зону.

## Интерфейс

![Журнал: фильтры, карточка нарушения с кадром, разбор](docs/images/journal.jpg)

- **Камеры:** одна камера или видеостена, рамки поверх видео, честный статус потока.
- **Зоны** рисуются кликами прямо по видео.
- **Журнал:** кадр, кадр без рамок и клип; разбор «подтвердить / ложное / передать мастеру»; выгрузка в Excel и отчёт за смену для печати.
- **Аналитика** по часам, дням и типам, доля ложных по отметкам операторов.
- **Производительность:** время каждой модели, кадры в секунду по камерам, задержка до события.
- **Роли:** администратор и оператор.

## Запуск

```powershell
powershell -ExecutionPolicy Bypass -File scripts\demo.ps1
```

Скрипт ставит недостающее, поднимает сервис, добавляет камеры для роликов из `data\videos` и открывает http://localhost:5173. Вход: `admin` / `admin1234`. В Docker: `scripts\demo.ps1 -Docker`, без видеокарты — `-Docker -Cpu`.

Свои файлы можно загрузить из интерфейса: «Камеры → Добавить камеру → Загрузить файлы…». Видео станет камерой, картинки или zip — набором стоп-кадров.

<details>
<summary>Установка по шагам</summary>

Нужны Python 3.12, Node.js 20+, ffmpeg в PATH; для Docker — Docker Desktop. Видеокарта NVIDIA желательна: без неё сервис работает на процессоре, но держит меньше камер.

1. **Модели и видео** (в git их нет):

   ```
   models/{ppe,hazard,people,heads}/best.onnx + model.yaml
   data/videos/*.mp4
   ```

   `people` собирает `scripts\make_people_model.py`, `ppe` и `hazard` копирует `scripts\sync_models.ps1`.

2. **Настройки:** `Copy-Item .env.example .env`. В `.env` лежат токен Telegram, секрет воркера, пароли учёток. Остальное — в `config.yaml` и в интерфейсе.

3. **Запуск:**

   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\setup.ps1   # один раз
   powershell -ExecutionPolicy Bypass -File scripts\dev.ps1     # MediaMTX, backend, воркер, интерфейс
   ```

   или

   ```powershell
   docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
   ```

**Живая камера:** тип источника `rtsp`, адрес вида `rtsp://user:pass@192.168.1.64:554/stream1`. Лучше брать субпоток 960×540: его декодирование в 2–3 раза дешевле.

**Telegram:** токен в `TELEGRAM_BOT_TOKEN`, включить в «Настройки → Telegram», написать боту `/start`.

**Вебхуки и REST:** [docs/API.md](docs/API.md).
</details>

<details>
<summary>LinQ TPU</summary>

Модели скомпилированы в int8 и работают на TPU стенда через облачную очередь. Что пришлось решить:

- **Упаковка кадра.** Облако упаковывает float32 около секунды на запрос, поэтому кадр в int8 пакуем сами, бит в бит с SDK: пачка из 8 кадров — 26 мс на кадр.
- **Пороги под int8.** Квантование сжимает уверенность модели в 4–7 раз, поэтому пороги подобраны отдельно. Полнота по событиям выросла с 0.17 до 0.70–0.78.
- **Весь воркер на стенде.** Декодирование, модели, трекинг и правила работают рядом с TPU, наружу уходят только события.
- **Живая камера через VPN.** ПК шлёт JPEG, стенд возвращает рамки (режим `relay`).

```powershell
python scripts\linq_remote.py sync
python scripts\linq_remote.py sh "python scripts/linq_pipeline.py --cams 1 2 --seconds 60"
```

Компиляция, квантование и все замеры: [docs/LINQ.md](docs/LINQ.md).
</details>

<details>
<summary>Новое нарушение</summary>

Правила работают по трекам людей, поэтому новый тип не требует переделки пайплайна:

1. `shared/schemas.py` — тип в `EventType` и класс параметров правила;
2. `worker/app/rules/checks.py` — функция проверки;
3. `worker/app/rules/engine.py` — подключение в `evaluate_track`, жизненный цикл события общий;
4. `config.yaml` — значения по умолчанию, дальше они правятся в интерфейсе;
5. подписи — `frontend/src/types.ts`, `backend/app/api/events.py`.

Если нужен новый класс на кадре, рядом с весами кладётся `models/<модель>/model.yaml` с классами и порогами.
</details>

## Ограничения

- Падение и «лежит неподвижно» ловим хуже всего (1–2 из 4 и 0–1 из 3): правило работает по форме рамки. Следующий шаг — модель позы.
- Жилет и маска — самые слабые классы СИЗ: в обучающих данных их мало.
- Ролики крутятся по кругу. На стыке треки получают новые номера, и нарушение открывается заново; на живой камере этого нет.
- Веса YOLOv8 под AGPL-3.0: для внедрения нужна коммерческая лицензия или модель под Apache-2.0. Пайплайн от этого не меняется.
