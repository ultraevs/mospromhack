# Сервис контроля нарушений промышленной безопасности по видео

Видео с камер → детекция (модели `ppe` и `hazard`) → правила → события → интерфейс, телеграм, вебхуки.

Находит: человека без каски, без маски, без жилета, вход в запретную зону, курение, огонь, дым. На каждое событие сохраняет стоп-кадр и клип.

- API: `docs/API.md`
- Инференс на ускорителе LinQ (компиляция, квантование, замеры): `docs/LINQ.md`

На RTX 3060 и i7-9700KF сервис держит 12 потоков 1080p при 6 кадрах в секунду на камеру (на грани) и 16 потоков при 4 кадрах в секунду (`PPE_FPS=4` в `.env`).

## Быстрый запуск

```powershell
powershell -ExecutionPolicy Bypass -File scripts\demo.ps1
```

Скрипт ставит недостающее, запускает сервис, добавляет камеры для видео из `data\videos` (если камер ещё нет) и открывает http://localhost:5173. Остановка: Ctrl+C в этом окне.

То же в Docker: `scripts\demo.ps1 -Docker` (с видеокартой) или `scripts\demo.ps1 -Docker -Cpu`.

## Что нужно на машине

| | запуск в Windows | запуск в Docker |
|---|---|---|
| Python 3.12 | да | нет |
| Node.js 20+ | да | нет |
| ffmpeg в PATH | да (`winget install Gyan.FFmpeg`) | нет |
| Docker Desktop (WSL2) | нет | да |
| Видеокарта NVIDIA со свежим драйвером | желательно | желательно |

Без видеокарты инференс идёт на процессоре: сервис работает, но держит меньше камер. Об этом пишется в логе воркера, в `/api/health` и на экране «Производительность».

Системная установка CUDA не нужна: библиотеки CUDA и cuDNN приходят вместе с `onnxruntime-gpu`.

## Запуск из чистой папки, по шагам

### 1. Модели и видео

В git их нет, они кладутся в папку руками или скриптом.

```
models/ppe/best.onnx       models/ppe/model.yaml
models/hazard/best.onnx    models/hazard/model.yaml
data/videos/*.mp4
```

Если на машине есть папка обучения, модели копирует скрипт (путь к `runs/` задаётся в `.env`, переменная `TRAIN_RUNS_DIR`):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\sync_models.ps1
```

Видео — любые записи с камер. Если их нет, `python scripts\make_test_video.py` собирает проверочный ролик из картинок тестовой выборки.

### 2. Настройки

```powershell
Copy-Item .env.example .env
```

В `.env`: токен телеграм-бота (пусто — бот выключен), общий секрет воркера и backend, порты. Всё остальное — в `config.yaml` и в интерфейсе на экране «Настройки».

### 3а. Запуск в Windows

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1   # один раз
powershell -ExecutionPolicy Bypass -File scripts\dev.ps1
```

`setup.ps1` создаёт `.venv`, ставит зависимости Python и интерфейса, создаёт `.env`, копирует модели, скачивает MediaMTX в `tools/` и проверяет, что onnxruntime работает на видеокарте.

`dev.ps1` поднимает MediaMTX, backend, воркер и интерфейс, логи пишет в `logs/`. Остановка: Ctrl+C; если окно закрыли, `scripts\stop.ps1`.

Один раз стоит выполнить `.\.venv\Scripts\python.exe scripts\export_dynamic.py`, затем `scripts\make_fp16.py`: первый делает вариант ONNX с динамическим батчем (инференс пачками), второй — файл половинной точности, с которым модель на видеокарте считает быстрее на четверть. `scripts\eval_map.py` проверяет, что точность при этом не упала. Исходные файлы моделей не меняются.

### 3б. Запуск в Docker

```powershell
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build   # с видеокартой
docker compose up -d --build                                                    # на процессоре
docker compose logs -f worker
docker compose down
```

Четыре контейнера: `mediamtx`, `backend` (в нём же ffmpeg для камер из файлов), `worker`, `frontend` (nginx). Папки `data/` и `models/` подключаются томами, в образы не попадают.

### Доступ в веб-интерфейс

Веб-интерфейс использует серверные cookie-сессии и роли. При первом запуске backend создаёт две учётные записи из переменных окружения: `AUTH_ADMIN_LOGIN` / `AUTH_ADMIN_PASSWORD` (полный доступ) и `AUTH_VIEWER_LOGIN` / `AUTH_VIEWER_PASSWORD` (оператор: камеры и журнал с разбором нарушений). В development по умолчанию это `admin` / `admin1234` и `viewer` / `viewer1234`; перед публикацией обязательно задайте собственные пароли. Администратор может создавать пользователей и менять их роли в разделе «Пользователи».

Про видеокарту:
- `docker-compose.gpu.yml` отдаёт воркеру видеокарту через NVIDIA Container Toolkit. В Docker Desktop на WSL2 он уже есть, нужен только драйвер NVIDIA в Windows.
- Если проброс не работает (ошибка про `nvidia` при старте контейнера), запускай без этого файла: воркер перейдёт на процессор.
- На чём реально идёт инференс, видно в `docker compose logs worker` (строка «воркер запущен: детектор onnx, устройство cuda» или `cpu`) и на экране «Производительность».

Про видео в браузере: WebRTC идёт из контейнера MediaMTX напрямую в браузер (порты 8889/tcp и 8189/udp). Для просмотра с другого компьютера в сети впиши IP машины в `.env`: `WEBRTC_HOST=192.168.1.20`.

Запуск в Windows и запуск в Docker занимают одни и те же порты, одновременно их не поднять.

### 4. Первые шаги в интерфейсе

1. **Камеры → Добавить камеру**: видеофайл из `data/videos` или адрес RTSP, обязательные СИЗ.
2. **Камеры** → нужная камера → вкладка «Зоны» → «Нарисовать зону», контур ставится кликами по видео. Запретная зона даёт событие «вход в запретную зону»; зона с горючими материалами включает правило «курение».
3. **Журнал**: фильтры, карточка нарушения с кадром и клипом, разбор: «подтвердить», «ложное», «передать мастеру». Ссылку на нарушение можно скопировать из адресной строки.
4. **Настройки → Telegram / Вебхуки**: куда и что отправлять.
5. **Производительность**: кадры в секунду по камерам, время инференса по моделям, задержка от кадра до события.

## Уведомления

**Телеграм.** Впиши токен в `.env` (`TELEGRAM_BOT_TOKEN=`), перезапусти backend и включи бота кнопкой в «Настройки → Telegram». После этого отправь боту `/start`. События высокой важности приходят сразу с фото и клипом, остальные — сводкой раз в минуту; тот же тип на той же камере не чаще раза в 5 минут. `/stop` отписывает чат.

**Вебхук.** Проверка руками: `python scripts\webhook_receiver.py --secret demo-secret`, затем в «Настройки → Вебхуки» добавь адрес `http://127.0.0.1:9100/hook` с тем же секретом и нажми «Проверить». Из Docker адрес приёмника на хосте — `http://host.docker.internal:9100/hook`, и приёмник надо запускать с `--host 0.0.0.0`. Формат и проверка подписи описаны в `docs/API.md`.

Замер числа потоков (сервис должен быть запущен, свои камеры лучше выключить):


Состояние процессов: http://localhost:8000/api/health. Производительность: экран «Производительность» или http://localhost:8000/api/stats.

## Если что-то не работает

| что видно | где смотреть |
|---|---|
| строка состояния на «Обзоре» красная | экран «Производительность» и http://localhost:8000/api/health |
| камера «Видео есть, анализа нет» | воркер не запущен или не взял камеру: `logs/worker.log`, экран «Производительность» |
| камера «Нет сигнала» | `logs/ffmpeg-cam-N.log`, `logs/mediamtx.log`; для RTSP — адрес камеры |
| видео чёрное, рамки есть | WebRTC не дошёл до браузера: порт 8189/udp, для Docker — `WEBRTC_HOST` |
| «инференс идёт на процессоре» | драйвер NVIDIA; `python -m worker.app.check_device` |
| воркер не отвечает | `logs/worker.log` или `docker compose logs worker` |
| бот молчит | «Настройки → Telegram»: статус, подписчики, порог важности |

## Известные ограничения

- Записи в `data/videos` крутятся по кругу. На стыке круга люди получают новые номера, и те же нарушения открываются заново; на живых камерах этого нет.
- Огонь и дым на живом видео не проверялись: записей с огнём не было.
- Старые стоп-кадры и клипы не удаляются сами (около 3 МБ на событие).
- Модели скомпилированы под LinQ TPU (int8, O1) и запущены на TPU стенда через облачную очередь. Для ppe mAP50 int8 0.753 против 0.734 у float, TPU ~6.8 мс/кадр, 4 камеры по 6 к/с идут с p95 200 мс. Цифры в `docs/LINQ.md`. Один чип LinQ на свободном TPU — 13–20 камер со всеми моделями (расчёт), на общем облаке стенда — 1–2 камеры (замер); раздел «Сколько камер тянет один TPU».
